# DreamLab — mock AI image generation

Бэкенд + Flutter-клиент под iOS. Пользователь пишет промпт, выбирает опции
(стиль, соотношение сторон, качество) и получает сгенерированную картинку.

Главное в этом проекте — **граница между клиентом и сервером**: генерация живёт
на бэкенде, клиент отправляет запрос, поллит статус, скачивает результат,
обрабатывает ошибки сети и неожиданные ответы, а историю держит у себя — так,
чтобы она переживала и перезапуск приложения, и недоступность бэкенда.

Никаких API-ключей, внешних сервисов и доступа в интернет: «картинки» рисует
процедурный art-движок на Pillow прямо в контейнере.

## 1. Быстрый старт

### 1.1 Бэкенд — одна команда

```bash
docker compose up --build
# → http://localhost:8000    (интерактивная документация: /docs)
```

В compose есть healthcheck, поэтому `docker compose up --wait` дождётся
готовности сервиса. Состояние (SQLite + PNG-файлы) лежит в `backend/data/`
через bind-mount и переживает `docker compose down` и рестарт контейнера.

Первый запуск тянет базовый образ `python:3.12-slim` и ~30 пакетов (всё
готовыми wheels — ни компиляции, ни сборки из исходников); после этого сервис
работает полностью офлайн.

Тесты прямо в контейнере:

```bash
docker compose run --rm api pytest tests/ -q     # 14 passed
```

Без Docker:

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Проверка: `curl http://localhost:8000/health` → `{"status":"ok"}`.

### 1.2 Клиент — Flutter на iOS-симуляторе

```bash
cd frontend
flutter pub get
flutter run -d "iPhone 16"
```

Требуется Xcode + iOS Simulator. Сборка без запуска:
`flutter build ios --simulator --no-codesign`.

### 1.3 Как их связать

Клиент по умолчанию ходит на **`http://127.0.0.1:8000`** — iOS-симулятор видит
хост-машину по loopback. Менять код не нужно: адрес редактируется прямо в
приложении.

**Settings → Connection → Server URL** → `http://127.0.0.1:8000` → *Test connection*.
Значение сохраняется и применяется к следующему запросу.

* На **реальном устройстве** адрес хоста — LAN-IP вашего Mac
  (`http://192.168.x.x:8000`); в `ios/Runner/Info.plist` включён
  `NSAppTransportSecurity → NSAllowsLocalNetworking`, иначе ATS режет
  plaintext HTTP.
* Контейнер слушает `0.0.0.0:8000`, поэтому бэкенд доступен и по
  `http://localhost:8000` с ноутбука.

## 2. Что умеет приложение

| Экран | Что делает |
|---|---|
| **Create** | Промпт, три группы опций (стиль / соотношение / качество), прогресс генерации, результат, ошибка с кнопкой *Try again* |
| **History** | Все генерации с превью, статусом и параметрами; тап — детализация; работает оффлайн |
| **Settings** | Адрес сервера и проверка связи, подписка и покупка, анонимный ID, очистка истории, сведения о приложении |
| **Paywall** | Bottom sheet со списком платных возможностей и мок-покупкой; после покупки отложенная генерация возобновляется сама |

Каталог опций клиент **не хардкодит** — он приходит с сервера (`GET /v1/options`),
поэтому стоимость и набор платных опций можно менять на бэкенде без релизов
клиента.

Весь интерфейс и тексты — на английском.

## 3. Граница клиент ↔ сервер

Источник правды — **сервер**. Клиент кэширует, но ничего не решает.

| Данные | Где правда | Кэш на клиенте | Что при расхождении |
|---|---|---|---|
| Каталог опций и флаги `premium` | сервер, `GET /v1/options` | JSON в `SharedPreferences` | Сначала рисуем кэш, потом тихо подменяем ответом сервера; при холодном старте без сети остаётся встроенный фолбэк |
| Статус подписки (`free`/`premium`) | сервер, `GET /v1/users/{id}/subscription` | тир в `SharedPreferences` | UI рисуется **сразу из кэша**, статус ревалидируется фоном; при ошибке остаётся кэш, и в Settings видно, что значение «из кэша» |
| Право на платные опции | сервер, 402 на `POST /v1/generations` | — | Клиент предупреждает заранее (пейвол до запроса), но **не решает**: запрос с премиум-опцией всё равно получает отказ |
| Статус генерации | сервер, `GET /v1/generations/{id}` | — | Кэшировать «почти готовую» картинку нельзя — только polling |
| История | клиент (sqflite) + сервер (таблица `jobs`) | sqflite + PNG-файлы в каталоге документов | History рисуется **local-first** (мгновенно, при выключенном бэкенде), затем мержится с сервером; если сервер недоступен — локальная история и баннер «server unavailable» |

**Идентификация.** Клиент при первом запуске генерирует анонимный `userId` (UUID)
и отправляет его **в каждом запросе** — в теле, в query и в пути подписки. Это
идентификация, а не авторизация: логина, паролей и экрана входа нет. Заодно это
работающая изоляция: чужой job отдаёт 404, а не картинку.

**Пока статус подписки ещё не приехал.** Три уровня рисуются немедленно, из
кэша — первый кадр не ждёт сеть. Как только ответ сервера пришёл,
`SubscriptionBloc` эмитит новый тир → `MultiBlocListener` в `app.dart` шлёт
`PremiumStatusChanged` в `GenerateBloc` → премиум-чипы разблокируются в тот же
момент, без перезапуска экрана.

**Оффлайн-история.** `HistoryStore` (sqflite) хранит метаданные (промпт, стиль,
статус, ошибка, `created_at`), PNG-файлы лежат в `Documents/generated/<job_id>.png`.
История переживает перезапуск приложения и работает при выключенном бэкенде.
При старте History сначала отдаёт локальные записи, потом best-effort
синхронизируется с сервером и догружает недостающие картинки.

В базе хранится только **имя файла**, а не абсолютный путь: при переустановке
приложения контейнер получает новый UUID, и сохранённый абсолютный путь указал
бы в пустоту. Имя файла переживает и переустановку, и перезапуск.

## 4. API

Интерактивная документация: `GET /docs` (сгенерированный OpenAPI).

| Method | Path | Назначение |
|---|---|---|
| GET | `/health` | liveness → `{"status":"ok"}` |
| GET | `/v1/options` | каталог опций: `styles`, `aspect_ratios`, `qualities` + флаг `premium` у каждой |
| POST | `/v1/generations` | принять job → **202** `{id, status:"queued", poll_url}` |
| GET | `/v1/generations/{id}?user_id=` | статус job-а: `queued \| processing \| succeeded \| failed` (+ `image_url` или `error`) |
| GET | `/v1/generations/{id}/image?user_id=` | PNG-байты (только для `succeeded`) |
| GET | `/v1/generations?user_id=&limit=` | серверная история пользователя |
| GET | `/v1/users/{id}/subscription` | `{tier: free\|premium, upgraded_at}` |
| POST | `/v1/users/{id}/subscription/upgrade` | мок-покупка подписки (без биллинга) |

Конверт ошибки — везде одинаковый:

```json
{
  "error": {
    "code": "premium_required",
    "message": "This request uses premium options. Upgrade your subscription to continue.",
    "details": { "required_options": ["quality:hd"], "upgrade_url": "..." }
  }
}
```

Коды: `premium_required` (402), `not_found` (404), `image_not_ready` (409),
`image_expired` (410), `validation_error` (422, с `details.fields` по каждому
полю), `generation_failed` / `server_restarted` / `internal_error` — в теле job-а.

Пример:

```bash
curl -s -X POST http://localhost:8000/v1/generations \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"11111111-1111-4111-8111-111111111111",
       "prompt":"sunset over the mountains","style":"cinematic",
       "aspect_ratio":"16:9","quality":"standard"}'
# → {"id":"…","status":"queued","poll_url":"/v1/generations/…"}

curl -s http://localhost:8000/v1/generations/<id>?user_id=11111111-1111-4111-8111-111111111111
# → {"status":"succeeded","image_url":"/v1/generations/<id>/image", …}
```

## 5. Как воспроизвести ошибку генерации

Ошибка не должна быть случайной — иначе её не увидеть с первого раза. Все
ошибки воспроизводимы намеренно:

| Сценарий | Как вызвать | Что получите |
|---|---|---|
| **Ошибка генерации** | добавьте слово **`fail`** в промпт (например `a cat, fail`) | job → `failed`, `error.code = "generation_failed"`, в приложении — красный блок с кнопкой *Try again* |
| **Сервер не отвечает** | добавьте слово **`timeout`** в промпт | job висит в `processing` дольше клиентского таймаута (30 с) → клиент показывает «Generation took too long» + *Try again* |
| **Отказ по подписке** | free-пользователь выбирает платную опцию или шлёт такой запрос напрямую в обход UI | **402** `premium_required`, `details.required_options`, `details.upgrade_url` → клиент открывает пейвол, а не «невнятную ошибку» |
| **Случайные сбои** | `FLAKY_RATE=0.2 docker compose up` | ~20 % генераций падают с `generation_failed` |
| **Рестарт сервера во время генерации** | отправьте job и перезапустите сервис, пока он `processing` | job становится `failed` с `error.code = "server_restarted"`; история и подписка выживают |
| **Неизвестный id** | `GET /v1/generations/doesnotexist` | 404 `not_found` |
| **Некорректное тело** | `prompt` короче 3 символов | 422 `validation_error` + список полей |
| **Чужой job** | `GET /v1/generations/<чужий id>?user_id=<свой>` | 404 `not_found` — история изолирована по анонимному ID |
| **Сервер недоступен** | выключить бэкенд | клиент: «Cannot reach http://127.0.0.1:8000…» + *Try again*; история и каталог опций продолжают работать из кэша |

Переменные окружения: `DATA_DIR`, `MIN_DELAY_SECONDS` (3), `MAX_DELAY_SECONDS` (8),
`FAIL_KEYWORD` (`fail`), `TIMEOUT_KEYWORD` (`timeout`), `TIMEOUT_DELAY_SECONDS` (30),
`FLAKY_RATE` (0).

## 6. Продуктовые решения

**Что платное и почему.** Бесплатный tier должен давать картинку «сразу и всем»,
а подписка — продавать то, что действительно дороже стоит провайдеру:

| | Бесплатно | Pro |
|---|---|---|
| Стили | Photorealistic, Illustration, Minimal | Cinematic, Cyberpunk, Watercolor |
| Соотношение | 1:1, 16:9, 9:16 | 21:9 (cinema) |
| Качество | Standard (1024px) | HD (2048px), 4K (4096px) |

Premium-стили и 21:9 — это продуктовая дифференциация, а HD/4K — прямая
имитация того, за что в реальных генераторах берут деньги: больше пикселей и
дольше рендер.

**Где стоит пейвол.** В трёх местах, но без тупиков:

1. **Проактивно, до запроса.** Платные опции видны в каталоге, помечены
   PRO-бейджем и «замочком». Если free-пользователь выбрал платную опцию,
   кнопка Generate открывает bottom sheet с пейволом — запрос ещё не ушёл.
2. **Реактивно, обработка 402.** Если запрос с платной опцией всё же дошёл до
   сервера (прямой curl, гонка с апгрейдом, старый клиент), сервер отвечает 402,
   а клиент превращает это в **тот же пейвол** — с перечнем недостающих опций.
3. **Возврат в флоу.** «Покупка» — один POST `…/subscription/upgrade`. Как только
   сервер подтвердил `premium`, пейвол закрывается сам, а отложенная генерация
   **перезапускается автоматически** — пользователю не нужно жать Generate ещё
   раз.

## 7. Технические решения

**Почему FastAPI + Python.** Задача — «отдать мок-данные и честно умереть».
Python + FastAPI дают это за вечер и дают типизированный контракт (Pydantic),
который потом читает клиент. Деплой — один `Dockerfile`.

**Почему форма API «202 + polling».** Раздача картинки — операция на несколько
секунд, и результат может не появиться. Варианты: синхронный запрос с
задержкой, SSE/websocket, polling. Выбран polling:

* переживает обрыв сети на мобильном без реконнект-логики — клиент просто
  продолжит поллить после восстановления;
* состояние job-а лежит в БД, а не в памяти процесса, поэтому переживает
  рестарт;
* его тривиально воспроизвести любым HTTP-клиентом (curl) и тривиально
  объяснить ревьюеру.

Клиент поллит с backoff'ом: 0.5 с → 2 с, жёсткий потолок 60 с.

**Почему SQLite, а не Postgres.** Задача прямо говорит, что Postgres здесь не
плюс. SQLite-файл переживает рестарт, не требует второго сервиса в compose и не
требует миграций. WAL-режим, индекс под историю пользователя.

**Почему очередь в процессе, а не Celery/Redis.** Долговечность обеспечивает БД:
при старте все `queued`/`processing` job-ы честно помечаются `failed`
(`server_restarted`) вместо того, чтобы делать вид, что они продолжатся.
Очередь в памяти процесса + состояние в SQLite = переживание рестарта без
инфраструктуры.

**Почему Pillow-генератор, а не диффузия.** Требование: работать на машине
ревьюера без регистраций и без интернета. Любая реальная модель — это либо
облачный API (нужен ключ и деньги), либо локальные веса (2–7 ГБ, нужен интернет
один раз и GPU). Поэтому «AI» — процедурный art-движок: fBm-шум, отдельные
сцены под каждый стиль (закатные пейзажи с отражениями в воде, городские
скайлайны, киберпанк с неоновой сеткой, акварельные заливки, геометрическая
иллюстрация, минимализм), ключевые слова промпта (`forest`, `city`, `night`,
`water`, `sunset`, `moon`, `stars`, `fog`, `snow`, `cloud`) выбирают элементы
сцены. На картинку накладывается «стеклянная» подпись с промптом и опциями —
видно, что запрос дошёл и параметры применились. Seed = sha256 от промпта,
стиля, соотношения, качества **и id job-а**: одинаковый вход даёт тот же арт,
но каждая генерация — новая вариация.

**Что на клиенте, а что на сервере.** На сервере — правила: каталог, премиум-гейт,
подписка, статус job-а, история. На клиенте — то, что обязано жить в телефоне:
история (переживает рестарт приложения и выключенный бэкенд), кэш каталога и
тира подписки (чтобы UI не мигал и был полезен оффлайн). Бизнес-логики на
клиенте нет: клиент умеет показать пейвол, но не умеет его обойти.

## 9. Что осознанно не сделано (и как бы сделал)

* **Настоящей генерации нет** — только процедурный art-движок. Это осознанный
  компромисс ради «работает без интернета и ключей». Следующий шаг: локальный
  **SD-Turbo** (~2.5 ГБ весов, 1–3 с на картинку на Apple Silicon) за флагом
  `IMAGE_BACKEND=local`, с моком по умолчанию; в проде — облачный API с
  очередью и ретраями.
* **Аккаунтов и авторизации нет** — только анонимный UUID, как и требовалось.
* **Настоящего биллинга нет** — «покупка» = один POST на сервер. Подключение
  StoreKit — отдельная задача, серверный контракт для неё уже готов.
* **Квотирования и rate-limit нет** (в моке они не нужны); в проде сюда
  добавился бы лимит генераций на пользователя.
* **UI-тесты — только unit/DTO**, без golden-тестов на скриншоты: время ушло бы
  на них, а не на границу клиент/сервер.
* **Удаления одной записи из истории нет** (есть «Clear local history» целиком) —
  мелочь, до неё не дошли.

## 11. Как использовался AI

Весь код написан AI-агентом — человек задавал фичи, принимал продуктовые
решения и ревьюил результат. Ниже — что сгенерировано, что переписано руками и
**где модель ошибалась и как это отлавливалось**.

**Сгенерировано AI (основной объём):** структура FastAPI-сервиса, схемы
Pydantic и SQL-схема, очередь job-ов, все эндпоинты и конверт ошибок, тесты
бэкенда, весь Flutter-код (DI-контейнер, блоки, dio-клиент с маппингом ошибок,
DTO, go_router, тема, три экрана, пейвол, sqflite-хранилище истории, виджеты),
Dockerfile, compose и этот README.

**Переписано руками (по итогам ревью):**

1. **Процедурный генератор.** Первый вариант давал плоские градиентные пятна
   вместо картинки. Переписано полностью: fBm-шум, отдельные сцены под каждый
   стиль, отражения в воде, keyword-детектор по промпту, bloom/vignette/grain.
   Все 6 стилей отсмотрены и перерисованы по мелочи (артефакты glow,
   прямоугольные «шлейфы»).
2. **Тема.** Сначала была тёмная неоновая — по фидбеку заказчика заменена на
   светлую (фон `#F4F4F8`, карточки с обводкой, акцент индиго, PRO — янтарь).
   `ShaderMask`-градиенты убраны: они съедали контраст текста.
3. **Детерминизм генерации.** Изначально одинаковый промпт давал байт-в-байт
   одинаковую картинку, и заказчик справедливо заметил, что «ничего не
   поменялось». В seed добавлен id job-а: тот же вход → тот же арт, но каждая
   генерация — новая вариация.
4. **Хранение картинок.** Изначально в БД писался абсолютный путь к PNG;
   после переустановки приложения превью в истории превращались в плейсхолдеры
   (контейнер получает новый UUID). Переписано на хранение имени файла с
   резолвом пути в рантайме, добавлена миграция БД v1 → v2 и автодокачка с
   сервера, если файла нет на диске.

**Где модель ошибалась и как это поймали:**

| Симптом | Причина | Как обнаружили и починили |
|---|---|---|
| `size.isFinite` assertion, экран в красных полосках | `Stack` со **всеми** `positioned`-детьми внутри `ListView` пытался взять `biggest` = ∞ | поймали при первом запуске на симуляторе; контент вынесен обычным (не `positioned`) ребёнком |
| `RenderFlex overflowed by 17 pixels` на строке ASPECT RATIO | `Row` внутри `ChoiceChip.avatar`: Flutter даёт `avatar` более узкие внутренние ограничения, чем `label` | поймали на симуляторе; иконки перенесены из `avatar` в `label` (паттерн, который уже работал у STYLE-чипов), рядок с опциями — горизонтальный `ListView.separated` |
| Прямоугольные артефакты вокруг glow | `GaussianBlur` клампится у границ спрайта | нашли на отрендеренных PNG; маска умножается на border-fade |
| `TypeError` в цветовых хелперах | `_lerp_color`/`_vgrad` принимали только hex-строки, а вызывались с RGB-кортежами | добавлен `_as_rgb`, принимающий оба формата |
| Премиум-опция проходила на free-пользователе | проверка была только в клиенте | перенесена на сервер: `POST /v1/generations` отдаёт 402 **до** постановки в очередь; проверено curl-ом и тестом |
| Каталог опций в клиенте разъезжался с серверным | модель захардкодила список на клиенте | клиент строит пикеры из `GET /v1/options`; в коде остался только фолбэк на случай оффлайна |
| `user_id` не уходил в polling и загрузку картинки | id добавили в тело запроса и в историю, но не в остальные вызовы | нашли при сверке с ТЗ («кладёт его в каждый запрос»); сервер теперь изолирует чужие job-ы 404-ом, покрыто тестом |
| Превью истории пустые после переустановки приложения | в БД хранился абсолютный путь, контейнер при переустановке получает новый UUID | поймали на скриншоте пользователя и инспекцией БД симулятора (`exists=False` при живом файле); исправлено хранением имени файла + миграцией + автодокачкой |

**Проверка вместо доверия.** Каждое изменение проходило через `pytest` (14/14),
`flutter analyze` (0 issues), `flutter test` (5/5) и
`flutter build ios --simulator --no-codesign`. Внешние картинки не «верили на
глаз» — рендеры сравнивались между собой и с тем, что видит пользователь
(сравнение md5 со скриншотом помогло доказать, что генератор обновился, а не
что сломался).

## 12. Скринкаст (до 1.5 минуты)

Сценарий: **генерация → ошибка и восстановление → пейвол → настройки → история
после перезапуска**.

Сценарий автоматизирован, чтобы его можно было воспроизвести:

```bash
cd frontend
flutter test integration_test/screencast_test.dart -d <simulator-id>
```

`frontend/integration_test/screencast_test.dart` проходит по реальному UI:
вводит промпт → *Generate* → ждёт картинку → вводит промпт с `fail` → видит
ошибку → жмёт *Try again* → выбирает платную опцию `4K` → пейвол → *Upgrade*
(после покупки генерация возобновляется сама) → Settings → History.

Запись видео:

```bash
xcrun simctl io booted recordVideo --codec=h264 demo.mp4
# Ctrl-C останавливает запись
```

Финальный кадр — **после перезапуска приложения**:

```bash
xcrun simctl terminate booted com.example.testAppAi
xcrun simctl launch booted com.example.testAppAi
```

затем вкладка History: история и картинки на месте, потому что они лежат в
локальном хранилище (см. раздел «Граница клиент ↔ сервер»).
