# DreamLab — mock AI image generation (backend + Flutter iOS client)

Один репозиторий, две части:

| Папка | Что внутри | Стек |
|---|---|---|
| [`backend/`](backend/) | REST-сервис: асинхронная «генерация» картинок, опции, подписка, история | Python 3.12 · FastAPI · SQLite · Pillow |
| [`frontend/`](frontend/) | Flutter-приложение под iOS: генерация, пейвол, история, настройки | Flutter 3.41 / Dart 3.11 · flutter_bloc · go_router · dio · sqflite |

Пользователь пишет промпт, выбирает стиль / соотношение сторон / качество, ждёт
картинку. Генерация живёт **на сервере**: клиент только отправляет запрос, поллит
статус, скачивает результат и умеет пережить падение/недоступность бэкенда.

Никаких внешних сервисов, API-ключей и интернета: «картинки» рисует процедурный
движок на Pillow прямо в контейнере.

## 1. Быстрый старт

### 1.1 Бэкенд — одна команда

```bash
docker compose up --build            # из корня репозитория
# → http://localhost:8000   (OpenAPI: http://localhost:8000/docs)
```

В compose есть healthcheck (`GET /health`), поэтому `docker compose up --wait`
дождётся готовности сервиса. Тесты прямо в контейнере:

```bash
docker compose run --rm api pytest tests/ -q     # 14 passed
```

Состояние (SQLite + PNG-файлы) лежит в `backend/data/` через bind-mount и
переживает `docker compose down` и рестарт сервиса.

Без Docker (нужен Python 3.11+):

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

(`docker-compose.yml` лежит в корне репозитория — контекст сборки `./backend`.)

Проверка, что сервис жив: `curl http://localhost:8000/health` → `{"status":"ok"}`.

> На dev-машине Docker не был установлен, поэтому образ не собирался «вживую».
> Вместо этого проверено всё, от чего зависит сборка: метаданные PyPI для всех
> пинов (совместимы с Python 3.12, wheels под cp312/manylinux есть — включая
> abi3-`watchfiles` из `uvicorn[standard]`, т.е. Rust-тулчейн не нужен), тег
> `python:3.12-slim` в Docker Hub, раскладка образа (`app/` + `tests/`, без
> `.venv` и `data/` — добавлен `.dockerignore`), а также ровно та команда и те
> же env-переменные, что в `CMD`/`ENV` образа: `DATA_DIR=/srv/data uvicorn
> app.main:app --host 0.0.0.0 --port 8000` на чистой папке данных + healthcheck
> из compose. End-to-end сценарии (генерация, PNG, 402, апгрейд, `fail`, 422,
> 404) и все 13 тестов прогнаны именно в этой конфигурации.

### 1.2 Клиент — Flutter на iOS-симуляторе

```bash
cd frontend
flutter pub get
flutter run -d "iPhone 16"      # или -d <любой симулятор>
```

Требуется Xcode + iOS Simulator. Сборка без запуска: `flutter build ios --simulator --no-codesign`.

### 1.3 Как их связать

Клиент по умолчанию ходит на **`http://127.0.0.1:8000`** (iOS-симулятор видит
хост-машину по loopback). Адрес меняется на лету в приложении:

**Settings → Connection → Server URL** → `http://127.0.0.1:8000` → *Test connection*.
Поле сохраняется в `SharedPreferences` и перечитывается Dio перед каждым запросом,
поэтому менять код не нужно.

* На **реальном устройстве** адрес хоста — это LAN-IP вашего Mac
  (`http://192.168.x.x:8000`), а в `ios/Runner/Info.plist` уже включён
  `NSAppTransportSecurity → NSAllowsLocalNetworking` (иначе ATS режет plaintext HTTP).
* Бэкенд слушает все интерфейсы (`0.0.0.0:8000`) внутри контейнера, так что
  с ноутбука он доступен и по `http://localhost:8000`.

## 2. Что где крутится (граница клиент ↔ сервер)

Источник правды — **сервер**. Клиент кэширует, но не решает.

| Данные | Где правда | Кэш на клиенте | Что при расхождении |
|---|---|---|---|
| Каталог опций (стили/соотношения/качество, флаги `premium`) | сервер, `GET /v1/options` | JSON в `SharedPreferences` | Сначала рисуем кэш/фолбэк, потом тихо подменяем ответом сервера. Клиент **не хардкодит** список опций — он приходит с сервера, фолбэк есть только на случай cold-start без сети |
| Статус подписки (`free`/`premium`) | сервер, `GET /v1/users/{id}/subscription` | тир в `SharedPreferences` | UI рисуется **сразу из кэша** (никакого мигания/спиннера), фоном тир ревалидируется; при ошибке остаётся кэш и в Settings видно, что статус «из кэша» |
| Право на платные опции | сервер, 402 на `POST /v1/generations` | — | Клиент **не решает**, можно ли: он только предупреждает заранее (показывает пейвол до отправки). Если запрос всё же ушёл с премиум-опцией — сервер отвечает 402, клиент ловит его и открывает пейвол с перечнем недостающих опций |
| Статус job-а | сервер, `GET /v1/generations/{id}` | — | Клиент только поллит; кэшировать «почти готовую» картинку нельзя |
| История генераций | клиент (sqflite) + сервер (таблица `jobs`) | sqflite + PNG-файлы в каталоге документов приложения | History рисуется **local-first** (мгновенно, работает при выключенном бэкенде), затем мержится с сервером. Если сервер недоступен — остаётся локальная история + баннер «server unavailable» |

Идентификация: клиент при первом запуске генерирует анонимный `userId` (UUID) и
кладёт его в **каждый** запрос (`user_id` в теле, в query, в пути подписки).
Это идентификация, а не авторизация: логина, паролей и экрана входа нет.

### Что показывать, пока статус подписки ещё не приехал

Тири из кэша рисуются немедленно (первый кадр не ждёт сеть). Как только ответ
сервера пришёл, `SubscriptionBloc` эмитит новый тир → `MultiBlocListener` в
`app.dart` шлёт `PremiumStatusChanged` в `GenerateBloc` → премиум-чипы
разблокируются **в тот же момент**, без перезапуска экрана. Если сервер не
доступен — остаётся кэш (приложение остаётся рабочим, просто статус может быть
устаревшим).

### Оффлайн-история

`HistoryStore` (sqflite) хранит метаданные (промпт, стиль, статус, ошибка,
`created_at`), PNG-файлы лежат в `Documents/generated/<job_id>.png`. При перезапуске
приложения история на месте, даже если бэкенд выключен. При старте History
блок сначала отдаёт локальные записи, потом best-effort синхронизируется с
сервером (`GET /v1/generations?user_id=…`) и догружает недостающие картинки.

**В БД хранится только имя файла, а не абсолютный путь.** Это не косметика: при
переустановке приложения (`flutter run` переустанавливает его при каждом
запуске) iOS/simulator выдаёт контейнеру новый UUID, и абсолютный путь вида
`.../Data/Application/<UUID>/Documents/generated/x.png` начинает указывать на
несуществующий каталог — превью в истории молча превращаются в плейсхолдеры.
Имя файла переживает и переустановку, и перезапуск. Миграция БД (v1 → v2)
переписывает старые абсолютные пути в имена.

Второй слой защиты: при синхронизации с сервером файл докачивается не только
когда в БД нет имени, но и когда **файла физически нет на диске** (например,
контейнер пересоздали, а метаданные остались) — тогда картинка восстанавливается
с сервера автоматически.

## 3. API

Интерактивная документация: `GET /docs` (сгенерированный OpenAPI).

| Method | Path | Назначение |
|---|---|---|
| GET | `/health` | liveness → `{"status":"ok"}` |
| GET | `/v1/options` | каталог опций: `styles`, `aspect_ratios`, `qualities` + флаг `premium` у каждой |
| POST | `/v1/generations` | принять job → **202** `{id, status:"queued", poll_url}` |
| GET | `/v1/generations/{id}` | статус job-а: `queued \| processing \| succeeded \| failed` (+ `image_url` или `error`) |
| GET | `/v1/generations/{id}/image` | PNG-байты (только для `succeeded`) |
| GET | `/v1/generations?user_id=&limit=` | серверная история пользователя |
| GET | `/v1/users/{id}/subscription` | `{tier: free\|premium, upgraded_at}` |
| POST | `/v1/users/{id}/subscription/upgrade` | мок-покупка подписки (без биллинга) |

Конверт ошибки — везде одинаковый:

```json
{ "error": { "code": "premium_required", "message": "…", "details": { "…": "…" } } }
```

Коды: `premium_required` (402), `not_found` (404), `image_not_ready` (409),
`image_expired` (410), `validation_error` (422, с `details.fields` — по каждому
полю), `generation_failed` / `server_restarted` / `internal_error` — в теле job-а.

Пример:

```bash
curl -s -X POST http://localhost:8000/v1/generations \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"11111111-1111-4111-8111-111111111111",
       "prompt":"sunset over the mountains","style":"cinematic",
       "aspect_ratio":"16:9","quality":"standard"}'
# → {"id":"…","status":"queued","poll_url":"/v1/generations/…"}
```

## 4. Как воспроизвести ошибку генерации

Ошибки нельзя «подождать» — нужен предсказуемый способ. Вот все ручки:

| Сценарий | Как вызвать | Что получите |
|---|---|---|
| **Ошибка генерации** | добавьте слово **`fail`** в промпт (например `a cat, fail`) | job → `failed`, `error.code = "generation_failed"`, retryable — в приложении красный блок с кнопкой Retry |
| **Сервер не отвечает (таймаут клиента)** | добавьте слово **`timeout`** в промпт | job висит в `processing` дольше клиентского таймаута (30 c по умолчанию) → клиент показывает «Generation timed out» + Retry |
| **Отказ по подписке** | free-пользователь выбирает премиум-опцию (или шлёт такой запрос напрямую в обход UI) | **402** `premium_required`, `details.required_options`, `details.upgrade_url` → клиент открывает пейвол, а не «невнятную ошибку» |
| **Случайные сбои** | `FLAKY_RATE=0.2 docker compose up` | ~20 % job-ов падают с `generation_failed` |
| **Рестарт сервера во время генерации** | отправьте job и перезапустите сервис, пока он `processing` | job становится `failed` с `error.code = "server_restarted"`; история и подписка выживают (проверено тестом `test_inflight_job_fails_after_restart`) |
| **Неизвестный id** | `GET /v1/generations/doesnotexist` | 404 `not_found` |
| **Некорректное тело** | `prompt` короче 3 символов | 422 `validation_error` + список полей |
| **Сервер недоступен** | выключить бэкенд | клиент: `Cannot reach http://127.0.0.1:8000…` + Retry; история и каталог опций продолжают работать из кэша |

Env-ручки бэкенда: `DATA_DIR`, `MIN_DELAY_SECONDS` (3), `MAX_DELAY_SECONDS` (8),
`FAIL_KEYWORD` (`fail`), `TIMEOUT_KEYWORD` (`timeout`), `TIMEOUT_DELAY_SECONDS` (30),
`FLAKY_RATE` (0).

## 5. Продуктовые решения

**Что платное и почему.** Бесплатный tier должен давать картинку «сразу и всем»,
а подписка — продавать то, что реально дороже стоит провайдеру:

* Бесплатно: стили **Photorealistic / Illustration / Minimal**, соотношения
  **1:1 / 16:9 / 9:16**, качество **Standard (1024px)**.
* Pro: стили **Cinematic / Cyberpunk / Watercolor**, соотношение **21:9 (cinema)**,
  качество **HD (2048px)** и **4K (4096px)**.

Логика: premium-стили и 21:9 — это «продуктовая» дифференциация, а HD/4K —
прямая имитация того, за что в реальных генераторах берут деньги (больше пикселей
и дольше рендер).

**Где стоит пейвол.** В трёх местах, но без тупиков:

1. **Проактивно (до запроса).** Премиум-опции видны в каталоге, но помечены
   PRO-бейджем и зубчатым «замочком». При выборе премиум-опции free-пользователем
   кнопка Generate открывает bottom sheet с пейволом — запрос ещё не ушёл.
2. **Реактивно (обработка 402).** Если запрос с премиум-опцией всё же дошёл до
   сервера (прямой curl, гонка с апгрейдом, старый клиент) — сервер отвечает 402,
   клиент превращает это в **тот же пейвол** с перечнем недостающих опций.
3. **Возврат в флоу.** «Покупка» — один POST `…/subscription/upgrade`. Как только
   сервер подтвердил `premium`, пейвол закрывается сам, а отложенная генерация
   **перезапускается автоматически** (`GeneratePaywallDismissed` → `GenerateSubmitted`)
   — пользователю не нужно жать Generate ещё раз.

**Экраны.** Create (промпт + три группы опций + результат), History (список +
детализация), Settings (адрес сервера и проверка связи, подписка, идентичность,
очистка истории, «Reset identity & subscription»). Весь UI и тексты — на английском.

## 6. Технические решения

**Почему FastAPI + Python.** Задача — «отдать мок-данные и честно умереть»:
Python + FastAPI дают за вечер и типобезопасные схемы (Pydantic) для
контракта, который потом читает клиент. Деплой — один `Dockerfile`.

**Почему форма API «202 + polling».** Раздача картинки — операция на несколько
секунд, а результат может и не появиться. Варианты были: синхронный запрос с
задержкой, SSE/websocket, polling. Выбран polling, потому что:

* он переживает обрыв сети на мобильном без реконнект-логики — клиент просто
  продолжит поллить после восстановления;
* состояние job-а лежит в БД, а не в памяти процесса → переживает рестарт;
* его тривиально воспроизвести любым HTTP-клиентом (curl) и тривиально
  объяснить ревьюеру.

Клиент поллит с backoff'ом: 0.5 c → 2 c, жёсткий потолок 60 c.

**Почему SQLite, а не Postgres.** Задача однозначно говорит, что Postgres здесь
не плюс. SQLite-файл переживает рестарт, не требует второго сервиса в compose
и не требует миграций. WAL-режим, `idx_jobs_user_created` под историю.

**Почему очередь в процессе, а не Celery/Redis.** Durability обеспечивает БД:
при старте все `queued`/`processing` job-ы честно помечаются `failed`
(`server_restarted`) вместо того, чтобы делать вид, что они продолжатся. Очередь
в памяти процесса + состояние в SQLite = состояние переживает рестарт без
инфраструктуры.

**Почему Pillow-генератор, а не диффузия.** Требование: работать на машине
ревьюера без регистраций и без интернета. Любая реальная модель — это либо
облачный API (нужен ключ и деньги), либо локальные веса (2–7 ГБ, нужен интернет
один раз + GPU). Поэтому «AI» — процедурный art-движок: fBm-шум, сцены под
каждый стиль (закатные пейзажи с отражениями в воде, городские скайлайны,
киберпанк с неоновой сеткой, акварельные заливки, геометрическая иллюстрация,
минимализм), ключевые слова промпта (`forest`, `city`, `night`, `water`,
`sunset`, `moon`, `stars`, `fog`, `snow`, `cloud`) выбирают элементы сцены.
На картинку накладывается «стеклянная» подпись с промптом и опциями — видно,
что запрос дошёл и что параметры применились. Seed = sha256 от промпта, стиля,
соотношения, качества **и id job-а**: одинаковый вход даёт тот же арт, но
каждая генерация — новая вариация (иначе пользователь видит, что «ничего не
поменялось»).

**Что на клиенте, а не на сервере.** На сервере — правила (каталог, премиум-гейт,
подписка, статус job-а). На клиенте — то, что обязано жить в телефоне: история
(и переживать рестарт приложения и выключенный бэкенд), кэш каталога и тира
подписки (чтобы UI не мигал и был полезен оффлайн), очередь ретраев.
Никакой «бизнес-логики» на клиенте нет: клиент умеет показать пейвол, но не
умеет его обойти.

## 8. Что осознанно не сделано (и как бы сделал)

* **Настоящей генерации нет** — только процедурный art-движок. Это осознанный
  компромисс ради «работает без интернета и ключей». Ближайший шаг: поднять
  локальный **SD-Turbo** (~2.5 ГБ весов, 1–3 c на картинку на Apple Silicon) за
  флагом `IMAGE_BACKEND=local`, оставив мок дефолтом; в проде — облачный API
  с очередью и ретраями.
* **Аккаунтов и авторизации нет** — только анонимный UUID, как и просили.
* **Настоящего биллинга нет** — «покупка» = один POST на сервер. Прикручивание
  StoreKit-а — отдельная задача, серверный контракт для этого уже готов.
* **Квотирование и rate-limit** не реализованы (в моке они не нужны); в проде
  сюда же добавился бы лимит генераций на пользователя.
* **Тесты на клиенте — только unit/DTO**, без golden-тестов на UI: 5–8 часов на
  задачу ушли бы на скриншот-тесты, а не на границу клиент/сервер.
* **Истории нет удаления по одной записи** (есть «Clear local history» целиком) —
  мелочь, но не хватило времени.

**Сгенерировано AI (основной объём):** структура FastAPI-сервиса, схемы
Pydantic и SQL-схема, очередь job-ов, все эндпоинты и конверт ошибок, тесты
бэкенда, весь Flutter-код (DI-контейнер, 4 bloc-а, dio-клиент с маппингом
ошибок, DTO, go_router, тема, три экрана, пейвол, sqflite-хранилище истории,
виджеты), Dockerfile/compose и этот README.

**Переписано руками (по итогам ревью):**

1. **Процедурный генератор** — первый вариант модели давал плоские градиентные
   пятна вместо картинки. Переписано полностью: fBm-шум, отдельные сцены под
   каждый стиль, отражения в воде, keyword-детектор по промпту, bloom/vignette/grain.
   Все 6 стилей отсмотрены глазами и перерисованы по мелочи (артефакты glow,
   прямоугольные «шлейфы»).
2. **Тема** — сначала была тёмная неоновая, по фидбеку заказчика заменена на
   светлую (фон `#F4F4F8`, карточки с обводкой, акцент индиго, PRO — янтарь).
   `ShaderMask`-градиенты убраны — они «съедали» контраст текста.
3. **Детерминизм генерации** — изначально одинаковый промпт давал байт-в-байт
   одинаковую картинку, и заказчик справедливо заметил, что «ничего не поменялось».
   В seed добавлен id job-а: тот же вход → тот же арт, но каждая генерация —
   новая вариация.
4. **Хранение картинок** — изначально в БД писался абсолютный путь к PNG.
   На симуляторе это ломало превью истории после каждой переустановки
   приложения (контейнер получает новый UUID, путь указывает в пустоту) —
   поймали на скриншоте пользователя. Переписано на хранение **имени файла**
   с резолвом пути в рантайме + миграция БД v1 → v2 + автодокачка с сервера,
   если файла нет на диске.

**Где модель ошибалась и как это поймали:**

| Симптом | Причина | Как обнаружили и починили |
|---|---|---|
| `size.isFinite` assertion, экран в красных полосках | `Stack` с **всеми** `positioned`-детьми внутри `ListView` пытался взять `biggest` = ∞ | поймали при первом запуске на симуляторе; контент вынесен обычным (не `positioned`) ребёнком |
| `RenderFlex overflowed by 17 pixels` на строке ASPECT RATIO | `Row` внутри `ChoiceChip.avatar` — Flutter даёт `avatar` более узкие внутренние ограничения, чем `label` | поймали на симуляторе (в т.ч. при тёмной теме); иконки перенесены из `avatar` в `label` (паттерн, который уже работал у STYLE-чипов), рядок с опциями — горизонтальный `ListView.separated` |
| Прямоугольные артефакты вокруг glow | `GaussianBlur` клампится у границ спрайта | нашли на отрендеренных PNG; маска умножается на border-fade |
| `TypeError` в цветовых хелперах | `_lerp_color`/`_vgrad` принимали только hex-строки, а вызывались с RGB-кортежами | добавлен `_as_rgb`, принимающий оба формата |
| Премиум-опция проходила на free-пользователе | проверка была только в клиенте | перенесена на сервер: `POST /v1/generations` отдаёт 402 **до** постановки в очередь; проверено curl-ом и тестом `test_premium_option_rejected_for_free_user` |
| Превью истории пустые после переустановки приложения | в БД хранился абсолютный путь к PNG, а контейнер приложения при переустановке получает новый UUID | поймали на скриншоте пользователя + инспекцией БД симулятора (`exists=False` при живом файле); переписано на хранение имени файла, добавлена миграция БД и автодокачка с сервера |
| Каталог опций в клиенте разъезжался с серверным | модель захардкодила список на клиенте | клиент теперь строит пикеры из `GET /v1/options`; в коде остался только фолбэк на случай оффлайна |

**Проверка вместо доверия.** Каждое изменение проходило через
`pytest` (13/13), `flutter analyze` (0 issues), `flutter test` (5/5) и
`flutter build ios --simulator --no-codesign`. Внешние картинки не «верили на
глаз» — рендеры сравнивались между собой и с тем, что видит пользователь
(сравнение md5 с его скриншота и помогло доказать, что генератор обновился, а
не что сломался).

## Структура репозитория

```
backend/
  app/
    main.py              # FastAPI app factory, lifespan, error envelope
    config.py            # env-настройки (data dir, задержки, ключевые слова)
    models.py            # enum-ы, каталог опций, Pydantic-схемы
    api/routes.py        # HTTP-слой
    services/jobs.py     # asyncio-очередь job-ов
    services/generator.py# процедурный art-движок (Pillow)
    storage/db.py        # SQLite + schema.sql
  tests/test_api.py      # 13 тестов
  Dockerfile, docker-compose.yml, requirements.txt, README.md

frontend/lib/
  main.dart, app.dart    # DI-контейнер, тема, MultiBlocListener
  core/                  # api-клиент (dio→AppFailure), конфиг, ошибки, тема, виджеты
  data/                  # DTO, sqflite-история, prefs, репозитории
  di/app_container.dart  # сборка зависимостей
  features/
    generate/            # bloc + экран + виджеты + пейвол
    history/             # bloc + список + детализация
    settings/            # bloc + экран
    subscription/        # bloc (tier с сервера + кэш)
  router/app_router.dart # 3 таба + детализация поверх шелла
```
